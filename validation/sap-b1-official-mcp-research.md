# SAP Business One 官方 MCP 样例：可吸收的语义内容

后续实施记录：本报告第1—7节保留研究时点的判断；2026-10-21 已按用户要求吸收销售组内有充分依据的内容，结果见第8节及[销售规格](销售语义-规格契约.md#34-官方-mcp-样例的销售语义吸收2026-10-21)。其他候选仍未实施。

研究日期：2026-10-21。范围为 SAP 官方下载包的静态源码、随包文档，以及相关 SAP Help Portal 页面；本轮不安装、不运行 MCP Server，不登录 SAP，不修改语义模型、工作区或业务数据。

## 1. 已确认的官方样例与取证

SAP Help Portal 的 [MCP Server for SAP Business One - Sample Code](https://help.sap.com/docs/SAP_BUSINESS_ONE/bb89a9939c294f14a7f532f7e76ade9e/9bdaeca12a424e6f9e3a0f4354651829.html) 明确将样例归于 SAP Business One 10.0 FP 2608。下载链接来自该页实际渲染的 `this file`，最终指向 [SAP 官方源码 ZIP](https://help.sap.com/doc/a3145f6e106a43b989b14c4c5342742d/10.0/en-US/b1-mcp-server.zip)，而非第三方同名 GitHub 项目。

本轮归档指纹：ZIP 18,507,905 字节、108 个文件，SHA-256 为 `8ea0a9ee324d38f180fd1c6d4f523c9fc93741dc4bda64aaa1c302883d439348`；包内 `package.json` 版本为 `1.0.0`。以下源码位置均相对包内 `b1-mcp-server/`，行号对应该指纹，下载包未来更新后需重新定位。

**结论：值得吸收，主要价值是语义元数据的可靠来源、枚举映射及按需暴露方式；它不是一套已经完成的报表业务语义模型。** 样例动态读取目标公司 Service Layer 元数据，不能仅靠离线样例获得某个公司的全部字段说明与有效值。已有 LC／FC／SC、报价备选行、折扣阶段等业务边界仍须保留官方业务帮助、逐表字典和现场验证作为依据。

## 2. 最值得吸收入模型与来源校验的内容

### M-01：区分业务名、API 属性与数据库物理字段

**已确认的源码事实：** `src/services/b1-metadata-parser.ts:54-70,187-236,276-294` 分别解析 `Common.Label`、`SAPB1.TableName`、`SAPB1.ColumnName`。SAP 的 [Metadata Query with Annotation (OData V4)](https://help.sap.com/docs/SAP_BUSINESS_ONE/f110a154dd0f4c20bf7f3ebca9eeb794/bc9463949d4f4239a25792aa98633520.html?locale=en-US) 解释了这些注释的职责。

**对本模板的建议／推论：**

- 表级保留业务对象名称、物理表身份和事实粒度；字段级保留业务名称、精确物理列名，必要时补充常见 API 别名。
- 导入、来源审计或离线核对工具可维护 `Service Layer entity/property → 物理表/列` 的证据映射，减少凭英文相似度猜字段。
- 显示名称与别名主要帮助发现，不能替代金额、状态、日期、粒度等业务定义。不必在每个简单字段描述中重复 API 技术说明。
- 官方标签具有语言上下文；不能无条件覆盖本模板已审阅的中文、英文文案，也不能把标签短语视为完整业务契约。

当前模板已具备中文／英文显示名与物理列分离，本项主要补来源校验与必要别名，不构成重做模型的理由。源码在缺少表名注释时退回 entity 名称（`:56,235`），只是样例降级行为；对于 SQL 模型导入，不能把该退回值直接当成已经核实的数据库表。

### M-02：枚举必须使用数据库存储码，不能混用 API 名称与序号

**已确认的源码事实：** `b1-metadata-parser.ts:82-108` 通过 `SAPB1.ValidValue` 建立枚举名称与数据库码的双向映射；`src/tools/b1-schema-execute-handlers.ts:140-159,579-589` 向调用方提供名称与 `code`。上述官方 metadata 文档示例中，`BoCardTypes.cCustomer` 的 OData `Value` 是 `0`，而数据库 `ValidValue` 是 `C`；`cSupplier` 的对应值分别为 `1` 与 `S`。[官方枚举映射说明](https://help.sap.com/docs/SAP_BUSINESS_ONE/f110a154dd0f4c20bf7f3ebca9eeb794/bc9463949d4f4239a25792aa98633520.html?locale=en-US)

**建议／推论：** 在 `CardType`、`DocType`、`DocStatus`、`CANCELED`、`CurSource`、行类型等字段的语义与来源清单中明确数据库取值及业务含义；若加入 API 枚举别名，应显式标注三者区别，不能让 SQL 使用 `cCustomer` 或 `0` 去筛字符列。枚举缺失或出现新值时保留未知态，不能自动解释为最常见业务状态。

可先把 metadata 作为现有字段枚举的**第二证据来源**，与逐表字段字典对照；不能把某个共享 API 枚举所有成员无条件铺到每张单据表。比如报价与发票的取消角色并不因 API 共享类型就完全一致。本项不要求立即改变 MDL 契约或增加强制枚举校验。

### M-03：复杂对象与集合要携带父对象和路径上下文

**已确认的源码事实：** `b1-schema-execute-handlers.ts:162-221` 递归返回复杂类型相对当前 entity 的引用路径、父路径、深度与数组标志；`src/services/b1-metadata-manager.ts:139-151` 为当前 entity 解析复杂类型；`b1-metadata-parser.ts:278-285` 还读取 `SAPB1.ChildTableName`。随包 `docs/THREE_STEP_APPROACH.md` 展示先取实体，再展开 `DocumentLine` 以及更深层结构。

**建议／推论：** 标准销售 `DocumentLine` 等共享 API 类型，必须置于报价、订单、交货或发票的具体上下文中，才可映射到 `QUT1/RDR1/DLN1/INV1` 等不同物理表。模型表说明继续维护业务对象和一行代表什么；关系继续维护精确键与基数，不能根据集合结构自动推导任意 SQL 关联。

官方 metadata 文档说明集合／复杂属性与标量属性的注释范围不同；本包支持的 `ChildTableName` 也不能被当作所有版本都保证返回的稳定公共字段。若将来用于来源核对，应同时留存原 metadata、版本和实际表列证据。

### M-04：内部键和来源三元组值得作为字段定义继续保持

**已确认的源码事实：** `src/tools/b1-constants.ts:238-271` 区分内部 `DocEntry` 与可见 `DocNum`，并将 `BaseType/BaseEntry/BaseLine` 定义为来源对象类型、来源内部键及来源行号。`:168-232` 的样例流包含报价到订单、订单到交货、交货到发票，也支持订单直接到发票。[官方包](https://help.sap.com/doc/a3145f6e106a43b989b14c4c5342742d/10.0/en-US/b1-mcp-server.zip)

**建议／推论：** 这些内容与当前模板的来源键设计一致，可作为交叉佐证；关联仍使用真实行 `LineNum`，不能用显示单号、同物料或数组位置替代。表级可以简要说明对象在销售流程中的角色；实际关系条件由关系定义维护。

样例的流转清单是工作流工具的支持范围，**不是 SAP 全部合法来源路径的完整矩阵**。因此不能删除模板已由逐表字典证明的其他报价直接后续关系，也不能因为“发票到支付”出现在清单里就把收款连接为同一种 `BaseType/BaseEntry/BaseLine` 关系。

### M-05：UDF、UDT、UDO 与个人字段是公司上下文元数据

**已确认的源码事实：** `b1-metadata-parser.ts:59-63,190-193,293` 区分标准对象、UDT、UDO 和 `U_` 字段；`b1-metadata-manager.ts:188-221,232-306` 从具体表的 PersonalFieldsSetups 取得个人字段标记，并用表名加物理字段名匹配。`src/services/b1-discovery.ts:9-25,130-156` 按公司数据库隔离 metadata manager。[官方包](https://help.sap.com/doc/a3145f6e106a43b989b14c4c5342742d/10.0/en-US/b1-mcp-server.zip)

**建议／推论：** 这对工作区模型扩展有用，但属于目标公司层。公开标准模板不应复制某家公司 UDF、个人数据分类、字段值或访问授权。将来若支持敏感字段标记，可以把分类来源留在模型管理元数据中；真正授权、脱敏及审计必须由运行时执行，不能依赖一句字段描述。

## 3. 值得借鉴，但不应塞进表／字段描述的部分

| 样例内容与已确认源码位置 | 正确责任层 | 对本系统的建议／推论 |
| --- | --- | --- |
| `docs/THREE_STEP_APPROACH.md`：`find_entities → get_entity_schema → read/write`，复杂类型再按需展开 | Agent 与工具契约 | 先发现候选对象，再读取当前字段定义，再查询；不是增加一段“请遵循三步”的数据库表说明 |
| `b1-schema-execute-handlers.ts:544-612`：紧凑文本与完整 `structuredContent` 同时返回，枚举文字超过 20 个只展示部分 | 工具输出与运行时 | 区分展示摘要与机器完整结果；分页、截断与完整性交付不能靠业务描述解决 |
| `src/tools/b1-category-mappings.ts`：同一对象可属于多个业务分类 | 搜索索引／标签 | 可以补发现标签；当前模板的一表一组是浏览归属，两者可并存，不能据此重排用户已确认的七组 |
| `b1-metadata-manager.ts` 与 `b1-discovery.ts`：按需、按公司缓存 | 连接器与缓存 | 连接上下文、公司与版本隔离要由实现保证，不能只写在模型说明里 |
| `src/tools/b1-elicitation.ts` 与读取执行器中的确认、个人字段处理 | 执行安全与权限 | 写入确认、敏感读取确认、脱敏、认证与审计属于执行策略；本次语义研究不引入新写入流程 |

以上样例事实来自静态源码，不证明它在目标 SAP 版本可运行。另对当前本地模板与现有 catalog 纯函数做了离线匹配检查，结果见第7节；这不是完整 Agent 集成或自然语言验收。

## 4. 不能因为“官方样例”就直接吸收的简化

### N-01：样例状态常量不能替代逐表状态定义

`src/tools/b1-constants.ts:291-295` 将 `bost_Open`、`bost_Close`、`bost_Cancelled` 放在同一常量对象中。这只是该样例的代码内容，**不证明数据库 `DocStatus` 有第三个取消值**。当前模板已分离 `DocStatus` 与 `CANCELED`，并逐表说明原单／反向取消单；应保留现有设计。API 枚举仍要按实际 metadata 与逐表字典核对，不能把常量直接写成 SQL 值。[官方包](https://help.sap.com/doc/a3145f6e106a43b989b14c4c5342742d/10.0/en-US/b1-mcp-server.zip)

### N-02：样例的发票余额计算不是通用历史应收或跨币种公式

`src/services/b1-payment-service.ts:43-49` 直接使用 `DocTotal - PaidToDate`；`:209-216` 构造支付分配时固定 `InstallmentId: 1`。这些代码未同时表达本模板已经关注的三币、分期、取消、核销时点等边界。因此不能把它扩大成所有单据的欠款定义，更不能据此回退报价 `Paid*` 的适用性审查。它首先是一个简化收款工作流示例；更广泛结论需要独立证据与目标库验证。[官方包](https://help.sap.com/doc/a3145f6e106a43b989b14c4c5342742d/10.0/en-US/b1-mcp-server.zip)

### N-03：数组下标不应成为语义模型的来源行号

`src/services/b1-document-service.ts:123-138` 遍历来源行数组，并把循环下标写作 `BaseLine`。本轮不运行该流程，也不判断其所有受支持场景是否出错；但这一实现不构成“数组位置永远等于真实 LineNum”的业务证明。数据库模型应继续依赖已保存的行号。[官方包](https://help.sap.com/doc/a3145f6e106a43b989b14c4c5342742d/10.0/en-US/b1-mcp-server.zip)

### N-04：API 类型与键不能直接替代 SQL 物理约束

`b1-metadata-parser.ts:249-295` 解析 API 类型、字符串长度、列别名等，但该函数未建立完整的数据库 Decimal 精度、scale 或非空约束映射。当前 SQL 模型的类型、主键、非空和关系基数仍须由数据库目录及逐表字典核实；不能把 `Edm.Decimal` 或 API entity key 自动等同于某张物理行表的完整约束。[官方包](https://help.sap.com/doc/a3145f6e106a43b989b14c4c5342742d/10.0/en-US/b1-mcp-server.zip)

### N-05：FP 2608 metadata 查询扩展不应直接成为稳定生产依赖

SAP 的 metadata 文档明确提示：带这些查询参数的返回内容可能在未来修订变化，不应据此构建 Service Layer 扩展。当前研究支持把它作为**可选、按版本识别、可追溯的校验资料**；不支持立即替换现有稳定导入来源或让所有查询依赖这一接口。正式采用前应确认目标 SAP 版本和官方支持边界。[官方兼容说明](https://help.sap.com/docs/SAP_BUSINESS_ONE/f110a154dd0f4c20bf7f3ebca9eeb794/bc9463949d4f4239a25792aa98633520.html?locale=en-US)

## 5. 与本轮销售报价审查的关系

离线源码和随包文档没有给出 `CurSource`、`MainCurncy/SysCurrncy`、报价备选行、报价税额开关、行折扣与整单折扣阶段的完整静态业务定义。包中的 `Confirmed` 还用于公司绑定确认，不应误认为已经解释了报价确认字段。本轮也未从实际 Service Layer 取目标公司的 metadata。

因此样例能帮助我们**更可靠地找到与校验字段**，但不能据此认定[报价审查报告](sales-quotation-review-research.md)中的问题已经解决、推翻或被样例验证。销售报价仍应先补业务适用性与汇总边界；映射、枚举可以再交叉核验。

## 6. 建议采用顺序与待验证场景

1. **先做模型内容核对。** 逐项比对关键枚举、内部键和 API／物理字段映射，已有充分描述保持；报价场景以既有审查建议为主。必要增补放在字段、表或关系的责任层，不写成大段全局通用提示词。
2. **再评估可选取证工具。** 针对支持 FP 2608 的隔离公司，按需取得少量实体 metadata，保存公司匿名标识、SAP 版本、语言、时间和哈希；先与静态字典对照，不自动改模型。
3. **最后单独评审工具体验。** 若现有 Agent 有上下文膨胀、查错对象、未知枚举或结果截断，再采用分步发现、紧凑描述、结构化完整结果；这属于另一个实施范围。

以下是建议验证，均**未执行**：

| 场景 | 预期结果 |
| --- | --- |
| `cCustomer / 0 / C` 三种表示并存 | SQL 字段用真实存储码；API 枚举名、序号与物理值可追溯 |
| 同一 `DocumentLine` 出现在报价和订单 | 分别绑定具体物理行表；粒度、主键和金额适用性不串用 |
| 一个关键枚举缺注释或出现新值 | 显式记录未识别／待核实，不补成默认状态 |
| 目标公司缺少 FP 2608 扩展或字段注释 | 停止自动映射或回退到已验证来源，不将 API entity 名冒充物理表 |
| 两家公司有同名 UDF、不同个人字段分类 | 来源、缓存与实例扩展隔离，公开模板不携带客户定义 |
| `DocStatus=O/C` 与取消角色组合 | 保留本模板逐表 `CANCELED` 定义，不合成第三个 DocStatus |
| API 类型与数据库精度、nullable 不同 | 报告差异，保留物理目录作为 SQL 类型约束依据 |
| 一个单据展开多个明细集合 | 按各自粒度聚合，不能把 API 嵌套展示当作 SQL 任意扁平连接许可 |

本报告完成官方来源确认、静态比较与现有发现函数的限定离线核对，没有实施模型补丁、Service Layer 取证、真实业务流程或 Agent 问答验收。现阶段不需要为了引用该样例安装 MCP Server。


## 7. 与当前语义模型和发现机制的实际差异

本地模板的 `OCRD.CardType` 已正确说明 `C/S/L`，报价的开闭、取消、三币和来源复合键也已有独立定义。官方样例的最大新增价值是可追溯的映射证据及取得方式，不应把已有正确规则改回样例中的简化常量。

当前 `tbi.ai.agent_catalog` 的发现函数匹配模型或字段的技术名、显示名和描述，没有独立的 Service Layer 实体别名入口。使用本地模板离线调用生产 `catalog_output`，相同配置下：

| 检索词 | 当前匹配情况 | 可以吸收的内容 |
| --- | --- | --- |
| `报价` | 能发现报价相关对象 | 中文业务名称仍保留 |
| `OQUT` | 能发现报价头和引用其含义的报价行 | 物理技术名仍保留 |
| `Quotations` | 0个对象 | 增加经过官方映射确认的 API 实体别名候选 |
| `BusinessPartners` | 0个对象 | 将 API 实体名与 OCRD 的业务名称建立可检索对应 |

这个核对只证明给定字符串和当前离线模板的匹配差异，**不证明 Agent 必然查错或英文业务搜索全部失败**。模型已有翻译能力，API 实体别名与显示语言是不同职责；不要为了补别名覆盖现有显示名，也不要只新增一个不会被 catalog 消费的属性。正式支持独立别名字段或枚举结构需同步导入、冻结MDL、describe与兼容契约，本研究不自动实施这类接口变更。

采用位置建议如下：

| 内容 | 应放的位置 | 本轮状态 |
| --- | --- | --- |
| 已验证的数据库码、业务含义与适用边界 | 相应字段说明；需要结构化时另审字段枚举契约 | 候选，未修改模型 |
| API实体、业务名称、物理表／列对应关系 | 可追溯的来源映射；必要别名由发现机制消费 | 离线发现差异已核对，未实现别名支持 |
| 报价、订单、交货、发票的业务角色 | 对应表说明 | 当前已有，样例仅作交叉佐证 |
